# Грабли qmd — почему скилл делает именно так

qmd 2.8.x, модель эмбеддингов `embeddinggemma-300M-Q8_0`. Каждый пункт: что ломается → как обходим.

## Запрос

- **Plain `query` запрещён.** Без `searches` qmd сам расширяет запрос генератором (модель 1,2 ГБ, качается при первом вызове), сливает варианты и реранкает. Для русского автоэкспансия ненадёжна (upstream qmd#774): выдача плывёт без ошибки. → Всегда `searches:[{lex},{vec}]` + `intent`. `query` и `searches` в одном вызове — ошибка сервера.
- **Реранк выключаем.** В MCP по умолчанию `rerank:true`, `limit:10`. Реранкер Qwen3-Reranker-0.6B — ~610 МБ скачивания при первом вызове и 10–20 с на запрос даже на тёплом процессе; без него ~0,4 с при почти той же точности (hit@5 0,96 против 1,00 на эталонном наборе). → `rerank:false` всегда; `candidateLimit` без реранка ни на что не влияет. В CLI флаг — `--no-rerank`; `--rerank=false` парсер молча глотает.
- **FTS5 без русского стеммера.** `lex` — BM25 с префиксным совпадением: `пробиотик` находит «пробиотиков», обратное — нет. → В `lex` леммы или основы без окончаний; фразы в кавычках; `-слово` исключает.
- **Первый подзапрос весит ×2.** → Сильнейший сигнал ставить первым.
- **`minScore`** по умолчанию 0. Отсекать выдачу `minScore: 0.5` можно, но на коротких русских заметках так легко потерять верный ответ — лучше меньший `limit`.

## Индекс и векторы

- **Чанки усечены (upstream qmd#897).** Чанк длиннее ~510 токенов даёт мусорный вектор без ошибки. Обход — `QMD_EMBED_CONTEXT_SIZE=506` (стоит в `.mcp.json` и в `qmd-env.sh`), но он усекает большую часть чанков: хвосты длинных заметок и глубокие ячейки таблиц вектор не видит. → Такие места ищи через `lex`. Ручной `qmd embed` из своего терминала без этой переменной портит векторы — переиндексация только через скрипты плагина или с явным `QMD_EMBED_CONTEXT_SIZE=506`.
- **Модели прописываются в YAML.** После первой команды qmd сохраняет `models:` в `index.yml`, и переменные `QMD_EMBED_MODEL`/`QMD_GENERATE_MODEL` дальше игнорируются. → Смена эмбеддера = правка `models.embed` + `/memory-search reindex --full`.
- **`ignore` — только в YAML** (`collections.<имя>.ignore`), флага CLI нет. `qmd collection add` для существующего имени падает с «already exists» — не перезаписывает.
- **`qmd init` — никогда.** Он создаёт `.qmd/` в текущей папке, т. е. индекс внутри vault, который уедет в синк. Хуже: любой qmd, запущенный из этой папки или её подпапок, подхватывает локальный `.qmd/index.yml` вместо общего конфига — индекс раздваивается. Нашёл `.qmd/` в хранилище → попросить пользователя перенести её.

## Свежесть

- **Задержка обновления.** Poller (launchd) проверяет папки раз в 60 с, ждёт 20 с тишины и переиндексирует; раз в час — полный проход. Итого свежая заметка находится через ~1–2 минуты. → Не искать только что созданную заметку сразу; нужно срочно — `/memory-search reindex`.
- **Режим «только хук»** (Linux или отказ от launchd): индекс догоняется при старте следующей сессии Claude Code. Правки, сделанные в Obsidian во время сессии, до этого не видны.
- **Переиндексация одна за раз.** Скрипт держит lock; второй запуск печатает «уже идёт переиндексация» и выходит — это не ошибка. Два `embed` одновременно qmd тоже не допускает.

## MCP-сервер

- **Список коллекций читается при старте сервера.** Коллекции по умолчанию для поиска запоминаются в момент запуска `qmd mcp`, т. е. при старте сессии. → После `add`/`remove` (и после первой настройки) — перезапуск Claude Code. Признак: коллекция есть в `qmd collection list`, но её нет в MCP `status`.
- **Один процесс qmd на сессию.** Каждая сессия Claude Code поднимает свой stdio-сервер; после первого векторного запроса он держит модель — до ~0,5 ГБ RSS на сессию. 1–2 сессии — нормально, 5+ параллельных — заметно по памяти.
- **Сессия стартовала без qmd** (qmd поставили посреди сессии) → сервер не поднялся, инструментов нет до перезапуска.
- **`qmd status` в CLI** показывает индекс (Total, Vectors, pending), но не состояние MCP-сервера этой сессии — для него MCP-инструмент `status`.

## Поиск без qmd

- **Grep может молчать.** Если vault лежит в git-репозитории, где заметки в `.gitignore`, инструмент Grep их не видит. → `command grep -rIl "<ключ>" "<папка>"` — детерминированно и без учёта `.gitignore`.
